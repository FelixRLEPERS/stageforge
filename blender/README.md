# Blender → Godot asset pipeline (ADR-0004)

Blender is the **asset preparation** half of the StageForge render
layer: it turns `.blend` sources into `.glb` (glTF 2.0) files that the
Godot scene under `godot/assets/` imports. It never runs in the
real-time path — Godot renders, Blender prepares.

## Requirements

| | |
|---|---|
| Blender | **4.2+**; portable 5.0.1 at `D:\AstraForge\runtime\blender\blender-5.0.1-windows-x64\blender.exe` |
| uv / uvx | for the MCP bridge (`uvx mcp-for-blender`) |
| MCP bridge | [mcp-for-blender](https://github.com/ahujasid/mcp-for-blender) (PyPI `mcp-for-blender`, formerly `blender-mcp` — the old name is a compat wrapper) |

## One-time MCP setup

**1. Install the Blender addon** (copies a single `blender_mcp.py`
into Blender's user addons folder):

```powershell
# standard Blender install — discovered automatically:
uvx mcp-for-blender install-addon

# portable / non-standard Blender (this machine) — point it at the folder:
$env:BLENDERMCP_ADDONS_DIR = "$env:APPDATA\Blender Foundation\Blender\5.0\scripts\addons"
uvx mcp-for-blender install-addon
```

(On this machine the installer may print a `UnicodeEncodeError` *after*
copying — the file lands anyway; it is only the cp1251 console failing
to print a `→` glyph.)

**2. Start the addon's MCP server** — either

- in Blender: `N` sidebar → **BlenderMCP** tab →
  **Connect to MCP server** (server listens on `127.0.0.1:9876`); or
- from the command line (enables the addon and starts the server for
  you, window stays open):

```powershell
& 'D:\AstraForge\runtime\blender\blender-5.0.1-windows-x64\blender.exe' `
  --python G:\stageforge\blender\start_mcp_server.py
```

**3. opencode already has the servers** (`opencode.json`, local
config): `blender` → `uvx mcp-for-blender`, `godot` → node +
`GODOT_PATH`. After editing that config, restart the OpenCode session
once; the `blender.*` / `godot.*` tools then appear. Verified live in
this session: `get_addon_status` → Blender 5.0.1, protocol 15/15;
`godot.get_godot_version` → 4.5.1.

## Exporting assets

**Via MCP** (Blender server running):

ask the agent to create/prepare the object and export, or run
`execute_blender_code` with `bpy.ops.export_scene.gltf(...)`. This is
exactly how the Phase 2 check ran:

```
CUBE CREATED: MCP_TestCube
MATERIAL APPLIED: alpha=0.5
EXPORT RESULT=('FINISHED',) path=G:\stageforge\godot\assets\test_cube_mcp.glb bytes=1636
MCP CUBE TEST: PASS
CLEANUP OK, objects left: 3
```

**Headless** (no MCP, CI-friendly) — `export_for_godot.py`:

```powershell
# export an existing .blend
& 'D:\AstraForge\runtime\blender\blender-5.0.1-windows-x64\blender.exe' `
  --background scene.blend --python G:\stageforge\blender\export_for_godot.py -- `
  --output G:\stageforge\godot\assets\scene.glb

# Blender already has the scene open — just give --output
```

Verified on 2026-11-07 (Blender 5.0.1):

```
EXPORT OK: G:\stageforge\godot\assets\test_cube.glb (3676 bytes)   # exit 0
```

### What the exporter guarantees

- `GLB` — single binary, textures embedded (what Godot imports from
  `godot/assets/`);
- `export_materials="EXPORT"` + `export_image_format="AUTO"` —
  Principled BSDF survives and images keep their **alpha** (PNG is
  chosen automatically for translucent materials);
- modifiers applied; cameras/lights dropped (the Godot scene owns
  framing and lighting).

## Generated files

`godot/assets/test_*.glb` are smoke-test artifacts — ignored by
`godot/assets/.gitignore`, regenerated by the tests, never committed.
Real production assets in `godot/assets/*.glb` **can** be committed
normally (files produced by Blender belong to their author; Blender's
GPL does not touch them).
